# Интеграция `tools_src/` как tool-layer для LangGraph агента

## 1) Зачем это нужно

`tools_src/` уже реализует большую часть требуемого детерминированного функционала triage:

- работа с образами (проверка/конвертация в raw),
- сбор артефактов (pytsk3),
- базовая обработка/анализ артефактов и генерация HTML отчета,
- обогащение контекста (ipinfo, VT lookup),
- обертки для LangChain tools.

В нашей архитектуре LangGraph эти классы выступают как **tool-layer**: узлы графа вызывают методы классов, а LLM используется строго там, где нужен семантический анализ/summary.

## 2) Какие классы использовать и где

Источник: `tools_src/src/...`

### 2.1 `ImageProcessor`

- **Использование в узле LangGraph**: `ingest_image`
- **Функции**:
  - определение типа образа
  - конвертация в raw через `qemu-img`
  - метаданные/хеши

### 2.2 `TriageCollector`

- **Использование в узле LangGraph**: `fs_triage_agent` (часть “collect”)
- **Функции**:
  - OS detection (Linux-only)
  - создание `triage/<image>_<date>_<uuid>/`
  - сбор артефактов по `configs/triage.yaml`
  - выгрузка логов в `logs/raw/*`
  - подготовка `logs/clear/auth_full.log`

### 2.3 `TriageAnalyzer`

- **Использование в узле LangGraph**: `fs_triage_agent` (часть “analyze summaries”) и/или отдельный узел `triage_summaries`
- **Функции**:
  - загрузка triage результатов
  - LLM summaries по промптам
  - генерация HTML отчета (если используется как “классический pipeline”)

### 2.4 `ContextEnricher`

- **Использование в узлах LangGraph**:
  - `ip_enrichment` (ipinfo bulk)
  - `vt_lookup` (опционально, lookup по SHA256)
- **Функции**:
  - извлечение сущностей (IP/домены/хеши)
  - обогащение из внешних источников (ipinfo, VT)
  - точка расширения под MCP

### 2.5 `integrations/langchain_tools.py`

В `tools_src` есть `LangChainTools`, который оборачивает операции в LangChain `Tool`.

Для нашего проекта (LangGraph + GigaChat) рекомендовано:

- переиспользовать **сами классы** (`ImageProcessor`, `TriageCollector`, `ContextEnricher`) напрямую,
- либо адаптировать `LangChainTools.get_tools()` для интеграции в узлы, если потребуется совместимость с LangChain-agent execution.

## 3) Конфигурация triage и промптов

- `tools_src/configs/triage.yaml` — список артефактов и настройки коллектора
- `tools_src/prompt` — исходное ТЗ/промпт (как reference), а реальные промпты для нашего агента лежат в `prompts/`

В нашей спецификации:

- `docs/03-workflows-triage.md` описывает обязательные файлы-выходы и шаги,
- `docs/06-api-cli.md` фиксирует содержание отчета.

## 4) Логирование и .env

Требования из ТЗ:

- во всех модулях логирование в файл,
- логировать **запросы/ответы LLM**,
- ключи брать из `.env`.

Это отражено в `docs/07-security-and-forensics.md` и должно быть реализовано в финальной кодовой базе агента.

## 5) Как это стыкуется с Neo4j GraphRAG

`tools_src` генерирует файловые артефакты triage и HTML отчет.  
Наша система дополнительно:

- парсит triage-выходы в нормализованные сущности/связи,
- записывает их в Neo4j (в кейс-изолированную БД/контейнер),
- делает GraphRAG анализ и формирует итоговый вывод (который может дополнять HTML отчет или генерировать отдельный “аналитический” отчет).
